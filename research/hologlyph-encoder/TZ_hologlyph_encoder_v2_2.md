# ТЗ v2.2: Валидация кодировщика в Gr(4, ℝ^d) на LongMemEval

> Строк: 148 · Дата: 21.11.2026 · ТЗ v2 + дополнения к плану (§0.1 заполнен, §0.2)

**Исполнитель:** Claude Code. **Каталог:** `research/hologlyph-encoder/` в `genesis-live-core`. C-ядро, `csrc/` и `hologlyph/` не трогать.

**Цель:** фальсифицируемый ответ на один вопрос: даёт ли **геометрия подпространства** (энергия проекции на span из 4 граней) прирост качества извлечения по сравнению с сильными плоскими и многовекторными бейзлайнами, **при одинаковой входной информации и одинаковой размерности**.

## 0. Принципы (нарушение = невалидный эксперимент)

1. **Изолировать эффект геометрии.** Все методы получают одни и те же 4 представления чанка (текст, саммари, сущности, контекст). Различается только способ хранения и скоринга.
2. **Метаданные в v1 не кодируются в измерения.**
   - Октанты 1..7 (провенанс, доверие, время и т.д.) в этом эксперименте не используются: все 128 (или d) измерений отдаются семантике.
   - Если отдать 112 из 128 измерений метаданным, семантический поиск сломается, и эксперимент будет мерить не геометрию, а потерю информации.
   - Время и доверие — отдельный этап v2 (§8), через заголовок и реранк, а не через измерения эмбеддинга.
3. **Равная размерность.** Каждый метод считается в двух размерностях: d = 128 (та же проекция) и d = 384 (нативная).
4. **Статистика.** Все сравнения парные по вопросам: paired bootstrap (10k ресэмплов) с 95% CI и McNemar для бинарных hit@K. Разница без CI не считается результатом.
5. **Без подгонки на тесте.** Гиперпараметры (проекция, центрирование, K, промпты для саммари) выбираются на dev-сплите. Итоговые цифры — только на test-сплите (§3).

## 0.1 Бюджет и порядок прогона (заполнено 21.11.2026)

- **Дедупликация реплик** — по sha256 нормализованного текста по всем 500 haystack (фоновые сессии частично повторяются в разных вопросах). В отчёт — число реплик до и после дедупликации.
- **F1 и F2 — один LLM-вызов на уникальную реплику**, ответ в JSON `{summary, entities}`. Кэш на диск по ключу `sha256(model_id + prompt_version + role + text)`. F3 и эмбеддинги генерируются без LLM.
- **Сначала dev.** Полный пайплайн на dev (150 вопросов). Фактические токены, стоимость и время записываются. Затем экстраполяция на test, и **оценка показывается до запуска test**.
- **Лимит бюджета: $7.17** — остаток кредита Anthropic, общий на все ключи организации. Стоп-правило: если прогноз dev + test превышает лимит, после пилота остановиться и прислать отчёт.
  - **Факт пилота:** прогноз $13.06.
  - **Решение пользователя (21.11):** генерировать только dev (~$4.7 всего); test — после пополнения кредита.
- **Модель F1/F2: `claude-haiku-5-5`**, через Message Batches API (−50 %).
  - Режим: thinking выключен, effort `low`, структурированный вывод (JSON-схема), промпт `f12-v1` в `llm_f12.py`.
  - На test — та же модель и та же версия промпта.
  - **Отступление от ТЗ:** у Haiku 5.5 нельзя задать temperature (на нестандартное значение API отвечает 400). Воспроизводимость обеспечивает кэш на диске, а не temperature 0.
- **Пилот:** 500 реплик dev, случайная выборка, стратифицированная по роли и квартилям длины, прямые вызовы.

## 0.2 Дополнения к плану (21.11.2026)

1. **Лимит входа эмбеддера** (bge — 512 токенов, MiniLM — 256).
   - F0 обрезает сам эмбеддер.
   - F3 — не больше 128 токенов на каждого соседа.
   - B2 склеивается в порядке F1 + F2 + F0 + F3.
   - Доли обрезанных входов F0, F3 и B2 — в отчёт.
2. **Сбой LLM** (ошибка, невалидный JSON, отказ, пустое саммари) → F1 = F2 = текст F0, одинаково для всех методов. Доля таких реплик — в отчёт.
3. **Прогноз стоимости test** — только по уникальным репликам test, которых нет в кэше dev.
4. **Агрегация по вопросам.** Recall агрегируется по вопросу, bootstrap и McNemar тоже по вопросам.
   - Центрирование и PCA обучены на текстах dev-haystack, частично пересекающихся с test: трансдуктивно, без меток.
5. **Batches API может отвечать до 24 ч.** Эмбеддинги F0 / F3 и бейзлайны B0 / B1 считаются параллельно.

## 1. Данные

- **Датасет:** LongMemEval_S, cleaned release (`xiaowu0162/longmemeval-cleaned`, HF).
  - 500 вопросов, у каждого свой haystack (~48 сессий, ~500 реплик).
  - В разметке есть `answer_session_ids` и, где есть, evidence-реплики.
  - Перед стартом проверить структуру по репозиторию бенчмарка и записать в отчёт фактические числа.
- **Поиск только внутри haystack своего вопроса** (официальный протокол). Утечка между вопросами = баг; добавить ассерт.
- **Гранулярность:**
  - основная — **реплика или раунд** (turn-level);
  - дополнительная — сессия. На уровне сессий сильные бейзлайны (BM25 + vector) уже дают R@5 ≈ 95% и выше: там потолок, и +3 п.п. статистически не увидеть.
- Вопросы на отказ (`_abs`) исключить из метрик извлечения, отчитать отдельно.
- **LoCoMo** — опционально, как второй датасет, только после завершения LongMemEval.

## 2. Кодировщик (`encoder_v1.py`)

**Модели эмбеддингов:** `bge-small-en-v1.5` (основная), `all-MiniLM-L6-v2` (контроль). Версии моделей зафиксировать.

**4 представления на чанк:**
- F0 — текст реплики/раунда.
- F1 — саммари (1 предложение, ключевой факт).
- F2 — сущности, числа, предикаты.
- F3 — локальный контекст (±1–2 соседние реплики).

F1 и F2 генерирует LLM: одна фиксированная модель, промпт в репозитории, кэш на диск по хэшу входа. В отчёт — модель, стоимость и время генерации.

**Предобработка эмбеддингов:**
1. **Центрирование:** вычесть средний вектор, посчитанный на dev-корпусе. У sentence-эмбеддингов сильная анизотропия: без центрирования все подпространства делят общую компоненту, и S насыщается. Вариант «без центрирования» — одна строка абляции.
2. **Проекция 384 → 128:** PCA, обученная на dev-корпусе (основная); Gaussian/SRHT (абляция). Для d = 384 проекции нет.
3. L2-нормировка каждого вектора.

**Ортонормализация:**
- QR в **float64** (Householder или MGS с реортогонализацией), затем приведение к fp32.
- Проверка в fp32: ‖YᵀY − I‖_F ≤ 1e-5. Порог 1e-7 в fp32 недостижим (машинный эпсилон 1.2e-7).
- **Вырождение:** если σ_min(raw 4 векторов) < 1e-3, грань заменяется детерминированным (seed от id узла) случайным направлением, ортогональным остальным. Долю таких узлов отчитать.
- Добавку «ε·I₄» не использовать: размерности не сходятся (матрица 128×4).

**Запрос:** эмбеддинг вопроса, та же предобработка, вектор q̃ с ‖q̃‖ = 1. Веса октантов в v1 равномерные (w = 1).

## 3. Сплиты

Разбиение по вопросам, фиксированный seed, стратификация по типу вопроса: **dev 150 / test 350**. Всё обучаемое (среднее для центрирования, PCA) и все решения о гиперпараметрах — только на dev.

## 4. Сравниваемые методы (у всех одни и те же F0..F3)

| # | Метод | Скор |
|---|---|---|
| B0 | BM25 по тексту F0 | — (лексический контроль) |
| B1 | Flat-cosine по F0 | ⟨f0, q⟩ |
| B2 | **Flat-expanded**: один эмбеддинг конкатенации текстов F0+F1+F2+F3 | ⟨f, q⟩ |
| B3 | Flat-mean: среднее 4 эмбеддингов, нормированное | ⟨f̄, q⟩ |
| B4 | Multi-vector max-sim | max_f ⟨f, q⟩ |
| B5 | Multi-vector sum-of-squares **без** ортонормализации | Σ_f ⟨f, q⟩² |
| G1 | **Grassmann:** энергия проекции на span(F0..F3) после QR | ‖Yᵀq̃‖² |
| H | Гибрид: лучший из {B4, G1} + BM25 через RRF | — (практический потолок) |

Что отвечает на какой вопрос:
- **G1 против B2** — «геометрия или просто больше информации».
- **G1 против B5** — вклад ортонормализации.
- **G1 против B4** — сравнение с многовекторным бейзлайном.

Абляции G1: без центрирования; набор граней {F0,F1}, {F0,F1,F2}; d = 128 против 384.

**Замечание для отчёта:** ‖Yᵀq‖² не различает знак, поэтому q и −q дают одинаковый скор. Посчитать долю топ-10 G1, где Σ⟨f,q⟩ < 0 (совпадение «по антинаправлению»).

## 5. Метрики

- **Извлечение (основное):** recall_any@K и recall_all@K, K ∈ {1, 5, 10}; NDCG@10; MRR. Turn-level и session-level, по каждому типу вопроса отдельно.
- **Downstream QA** (этап 2, только если G1 проходит §6 по извлечению): фиксированная модель-читатель, официальный промпт и judge LongMemEval, top-10 контекста. Accuracy с 95% CI.
- **Латентность:** при ~500 узлах на вопрос она не является информативной метрикой. Отчитать brute-force на CPU одной строкой. Быстрый путь (LSH) в этом эксперименте не нужен.
- **Масштабный тест (опционально):** объединить haystack всех 500 вопросов в один пул (~250k реплик) и мерить recall вопроса среди чужих дистракторов. Только здесь подключается C-ядро (§7).

## 6. Решающее правило (зафиксировано до прогона)

Основная метрика — **turn-level recall_any@5 на test**, d = 128 и d = 384 отдельно. Сравнение с **сильнейшим** из B2, B3, B4, B5.

| Исход | Условие | Решение |
|---|---|---|
| **A. Подтверждение** | G1 − best_baseline ≥ +3.0 п.п., нижняя граница 95% CI > 0, в обеих размерностях | Грассман — базовое представление. Этап 2 (QA) и v2 с метаданными. Материал для препринта. |
| **Б. Неразличимо** | 95% CI разницы содержит 0 | Геометрия не даёт качества. Хранить многовекторно (B4/B5) с C99-гейтингом и детерминизмом. Грассман оставить только как кандидата для v2, где его оправдают метаданные. |
| **В. Опровержение** | Верхняя граница CI < 0 | Отказаться от подпространства в L2. Многовекторный индекс + C99-гейтинг. |

**Устойчивость к отравлению в v1 не меряется** и в решающее правило не входит. Это отдельный эксперимент §8 с собственным протоколом атаки.

## 7. Интеграция с C-ядром (только после §6, исход A или масштабный тест)

- Экспорт в формат узла `hologlyph` (64 B заголовок + 4×128 fp32). Раскладку проверить по фактическому `hologlyph.h`, а не по этому ТЗ.
- Сверка: скор C-моста совпадает с numpy-эталоном (|Δ| < 1e-5) на 1 000 узлах.

## 8. Вне скоупа v1 (зафиксировать в отчёте как план v2)

- **Время** (knowledge updates, temporal reasoning) — через timestamp в заголовке + реранк/затухание; сравнение с тем же реранком поверх B4.
- **Доверие и отравление** — протокол: внедрение N враждебных реплик в haystack (перефразы-противоречия); метрика — доля отравленных узлов в top-K с гейтингом и без.
