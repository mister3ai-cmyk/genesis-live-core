# rt_core — нативное ядро шлюза и геометрии роя (C99)

> Строк: 413 · Дата: 12.11.2026 · Ветка `s5-sync-multicast` · Лицензия BSL 1.1 (research/LICENSE)
> Содержимое: порт кинематического шлюза v4.0 в 3D и геометрии Gr(k, N) на C99; юнит-тесты (179 проверок, в том числе дрейф инкрементальных сумм на 10⁵ записей; исполняются и на aarch64 под qemu), сборка под Cortex-M4/M7 без ОС, оценка рассинхрона взаимной корреляцией, подписанный кадр GEP v0.1 Lite с карантином, синхронизация часов SYNC_PING/PONG, живая шина из 7 процессов ОС по UDP multicast, бенчмарк латентности, обёртка ctypes со сверкой против Python-эталона, эксперимент 6-DoF «рассинхрон IMU и позы», проверка на реальных полётах EuRoC MAV (V1_02, V2_02). Уровень S2: синтетика и записанные полёты, атаки и наблюдатели смоделированы, ноутбук, не бортовое железо.

## Правила ядра
- `-std=c99 -Wall -Wextra -Werror -pedantic`. Встраиваемые сборки — без libc и libm (`make embedded`, см. S4).
- Ни `malloc` и `free`: вся память в `rt_context_t`. Контекст выделяет вызывающий — статически, на стеке или из Python через `rt_ctx_size()`. Проверка — `make check-nomalloc` (`nm -u` по объектникам).
- Глобального изменяемого состояния нет.

## Шлюз: что изменилось против v4.0
- **Синхронность.** `FAILSAFE`, если метка заявки опережает локальное время больше чем на `max_skew` (50 мс): часы автора убежали. Метка в прошлом — это задержка доставки, она шлюз не выключает. Проверять |now − t| было бы ошибкой: при p95 задержки ~1 с в симуляторе шлюз почти всегда уходил бы в fail-safe.
- **Быстрый путь.** Если мой датчик ближе к заявке, чем `pos_tol`, спора нет, и прогноз не считается.
- **Инкрементальные суммы.** Суммы нормальных уравнений по каждому автору ведутся в `rt_kin_push`: новый отсчёт прибавляется, вытесненный из кольца вычитается. Хранятся в локальном времени кольца s = (t − t0)/1e6 с: Sₖ = Σsᵏ (k = 0..4), Bₖ = Σsᵏ·p (k = 0..2).
  - **Запрос:** суммы окна получаются биномиальным сдвигом к τ = s − s_q, без прохода по точкам. Точки вне окна — старше горизонта или «из будущего» при поздней доставке — вычитаются поштучно.
  - **Перебазирование:** t0 переносится, и суммы пересчитываются из кольца, когда метка уходит дальше 16 с от t0 или после 1024 вытеснений. Это ограничивает и рост s⁴, и накопленный дрейф.
  - Аккумуляторы `double`. Контекст вырос с 21 704 до 37 320 B.
- **Точные ускорения прогноза** (результат не меняется):
  - кандидат «без автора a» = итог минус суммы a;
  - если подгонка по всем авторам согласна со всеми точками, остальные кандидаты не считаются;
  - кандидат бросается, как только не может превзойти лучшего; невязка считается до превышения порога;
  - если согласны ровно все точки, кроме точек одного автора (лжец в окне), финальная подгонка берёт готовые суммы «итог минус автор».

## Результаты

**Тесты.** `make check` — 113 проверок на C. `check-nomalloc` — ок.

**Дрейф инкрементальных сумм.** 10⁵ записей подряд, 4 автора, координаты 10⁴–10⁷, 775 перебазирований. Максимальное относительное расхождение с прямым пересчётом — в суммах 6.7e-12, в прогнозе 1.1e-13.

**Сверка через ctypes:**
- 300 из 300 прогнозов C совпали с `kinematics.predict` с точностью 1e-6, из них 150 с лжецом в окне;
- то же при поздней доставке — запрос на 1.5 с раньше последних точек: 300 из 300;
- `rt_gr_chordal2` совпадает с numpy до 1e-12.

**Латентность.** i5-11400H, WSL2, gcc 15.2, по 3 запуска; накладные `clock_gettime` вычтены.

С лжецом в окне запас до 1 мкс небольшой: p50 — 0.88–0.91, p99 — до 0.99 мкс. Цифры сняты на обычной ОС (WSL2, ноутбук). Это не WCET и не бортовое железо.

**6-DoF: рассинхрон IMU и позы.** `pytest -s tests/test_sixdof.py`, 3 режима × 12 траекторий × 5 окон по 64 отсчёта IMU (0.32 с).
- **L** — невязка простого предиктора: ускорение и угловая скорость из квадратичной подгонки позы против IMU, приведённого в мир, с поправкой на центробежный член плеча.
- **G** — хордальное расстояние Gr(4, 64) между подпространствами каналов позы и IMU (C-ядро).

Ошибка лучшего порога: 50 % — угадывание, 0 % — полное разделение.

**Вывод.**
- При шуме визуальной одометрии рассинхрон до 50 мс на окне 0.32 с не видит ни один детектор.
- При точности уровня Vicon простой предиктор ловит рассинхрон 20–50 мс на манёврах. Подпись Gr(4, 64) остаётся на уровне угадывания при любом δ: даже без рассинхрона подпространства далеки (d² ≈ 2.75–3.0 из 4), потому что нормированные каналы с малым разбросом — в основном шум.
- Это второй отрицательный результат Грассмана против простого предиктора (первый — `SWARM_FINDINGS.md`, Часть XI, A2).
- Для калибровки рассинхрона нужен штатный инструмент — оценка задержки по взаимной корреляции (как во временной калибровке IMU и камеры). Он здесь не реализован.

### A. Шлюз на живой траектории
**Сценарий.** 4 виртуальных борта видят дрон по истине Vicon: 20 Гц на каждый, шум σ = 2 см; пятый борт — атакующий. Время общее. Пороги перенесены из симулятора в единицах σ: `pos_tol` 10σ, `drop_tol` 14σ. Горизонт и `thr` выбраны на первой половине V1_02 (все 12 комбинаций 0.5–4 с × 20–40σ дали 0 % ложных тревог и 99.7–100 % обнаружения), выбор — 0.5 с, 20σ.

**Проверка** (на калибровку не влияла):

| | Вторая половина V1_02 | V2_02 целиком |
|---|---|---|
| Ложные тревоги на честных заявках | 0.00 % из 3 080 | 0.00 % из 8 612 |
| То же в 10 % самых резких моментов (\|a\|, \|ω\|) | 0.00 % из 695 | 0.00 % из 1 630 |
| T8, сдвиг 20–50σ (0.4–1 м) по оси, опровергнуто | 100 % из 778 | 100 % из 2 164 |
| Скачок 1.5–3 м в моменты верхних 10 % угловой скорости | 100 % из 86 | 100 % из 223 |
| Свой грубый сбой: ошибочных опровержений | 0 из 431 | 0 из 1 140 |

**Стресс на V2_02.** Шлюз ловит ложь, которая заметно больше шума: начиная с 10σ, при 10–20σ — 98.3 %. Порог задаёт не динамика полёта, а `pos_tol`.

| Шум σ | Сдвиг лжи по оси | Ложные тревоги | T8 опровергнуто |
|---|---|---|---|
| 2 / 5 / 10 см | 5–10σ | 0 % | **0 %** — ниже `pos_tol`, спора нет |
| 2 / 5 / 10 см | 10–20σ | 0 % | 98.3 % |
| 2 / 5 / 10 см | 20–50σ | 0 % | 100 % |

- Цифры одинаковы при σ 2, 5 и 10 см. Квадратичная подгонка за 0.5 с описывает реальный полёт с ошибкой много меньше 2 см, поэтому всё масштабируется в единицах σ.
- Ложь меньше `pos_tol` по замыслу не оспаривается: это быстрый путь «спора нет». Ловить её — задача Марзулло и кворума, а не шлюза.
- **Латентность.** Через ctypes на реальном потоке p50 5.8–5.9 мкс, p99 19–23 мкс; основная доля — накладные расходы Python и ctypes. Сам шлюз в C — 0.5–0.9 мкс (бенчмарк выше).

### B. Gr(4, 64) на сравнении сегментов движения
**Подпись.** Каналы на 50 Гц: ускорение и гироскоп IMU, горизонтальная и вертикальная скорость; нормированы по всему полёту. Блочная матрица Ганкеля — 8 каналов × 8 задержек = 64 строки, окно 2 с. Подпись — 4 главных левых сингулярных вектора; расстояние — `rt_gr_chordal2`.

**Базовая линия.** Векторы простых признаков: среднее, разброс и мощность в 3 полосах по каждому каналу, 40 признаков.

398 сегментов с шагом 0.5 с. Классы размечены по истине: висение 43, пролёт 59, разворот 55, агрессивный 60, прочее 181.

**1. Сдвиг во времени.** Медиана расстояния до того же сегмента, сдвинутого во времени, делённая на медиану расстояния до случайного другого сегмента. Меньше — устойчивее к сдвигу.

| Сдвиг | Gr(4, 64) | Признаки |
|---|---|---|
| 0.10 с | **0.04** | 0.16 |
| 0.25 с | **0.15** | 0.33 |
| 0.50 с | **0.38** | 0.51 |
| 1.00 с | **0.57** | 0.74 |

**2. Однотипные против разнотипных.**
- Внутри класса d² ниже, чем между классами, для пролёта, разворота и агрессивного манёвра: на диагонали 2.16 / 1.98 / 2.01 против 2.17–2.73 вне её. У висения разделения нет: 2.34 на диагонали против 2.51–2.73 вне её — в основном шум.
- Классификация 1-NN (сосед не ближе 3 с по времени, n = 217): **Gr(4, 64) — 43.3 %, признаки — 62.7 %**, доля крупнейшего класса — 27.6 %.

**3. Нарушение физической связности осей** — расстояние до испорченной копии против медианы до однотипных сегментов:

| Порча | Gr(4, 64): медиана / > 1 | Признаки: медиана / > 1 |
|---|---|---|
| ось x акселерометра отстаёт на 20 мс | 0.008 / 0 % | 0.027 / 0 % |
| то же, 50 мс | 0.024 / 0 % | 0.037 / 0 % |
| обмен осей x и y (IMU) | 1.05 / 65 % | **13.7 / 100 %** |

**Вывод по B.**
- **Где Gr(4, 64) лучше:** устойчивость к сдвигу во времени. При сдвиге 0.1–1 с подпись меняется в 1.3–4 раза меньше, чем вектор признаков.
- **Где хуже:**
  - различение типов манёвров: 43 % против 63 %;
  - обнаружение нарушенных осей: обмен x и y признаки ловят в 100 % случаев, подпись — в 65 %.
- Задержку одной оси на 20–50 мс не видит ни то, ни другое: это задача оценки задержки по взаимной корреляции.
- Ниша подтверждена узкая: сравнение сегментов без выравнивания по времени. Как классификатор и как детектор порчи Gr(4, 64) уступает простой базовой линии. Это третий результат того же рода после `SWARM_FINDINGS.md`, Часть XI, A2, и 6-DoF.

## S4, шаг 1: встраиваемые цели и оценка рассинхрона

### Сборка без ОС
`rt_port.h`:
- обнуление и копирование памяти — своими циклами вместо `memset` и `memcpy`;
- `RT_FABS` и `RT_SQRT` — встроенные функции компилятора;
- при `RT_NO_LIBM` — `sqrt` по Ньютону: 6 итераций, ошибка ≤ 2 ulp, проверено от 1e-300 до 1e300.

Явные присваивания структур заменены копированием через `rt_copy`, иначе компилятор вставляет `memcpy`.

Флаги встраиваемой сборки:
- `-ffreestanding -fno-math-errno`;
- `-fno-stack-protector -U_FORTIFY_SOURCE` — Ubuntu-gcc иначе тянет `__stack_chk_fail` и `__memcpy_chk`, которых на голом железе нет;
- `-fno-tree-loop-distribute-patterns` — не превращать циклы обратно в `memset`.

| Цель (`make embedded`) | Что проверено | Внешние символы ядра | Код (text) | Стек `rt_kin_predict` |
|---|---|---|---|---|
| `cross-aarch64` (gcc 15.2) | все C-проверки (сейчас **179**) исполнены под `qemu-aarch64` | **нет** | — | — |
| `cross-m4` — Cortex-M4F, FPU одинарной точности, `RT_NO_LIBM` | компиляция, символы, размер | только libgcc для программной двойной точности: `__aeabi_dadd/dsub/dmul/ddiv/dcmp*/i2d/l2d` | 9 220 B | 4 672 B |
| `cross-m7` — Cortex-M7, FPU двойной точности | компиляция, символы, размер | только `__aeabi_l2d` (int64 → double) | 6 608 B | 4 608 B |

Остальные функции по стеку: `rt_kin_sums_check` около 1 КБ (только для тестов), `fit_sums` 224–280 B, `rt_kin_gate` 72–104 B, `rt_xcorr_delay` 64 B. Данных в секциях `.data` и `.bss` нет: всё состояние в `rt_context_t` (37 320 B), его размещает вызывающий.

**Что это значит для железа:**
- **Cortex-M4F и ESP32:** `double` считается программно, и латентность 0.5–0.9 мкс на них **не переносится**.
- **Cortex-M7 и AArch64:** `double` аппаратный.
- **Стек:** `rt_kin_predict` занимает около 4.6 КБ — для МК со стеком 2–8 КБ это существенно. Сократить можно, храня точки окна во `float`, — не сделано.
- **Запуск на эмуляторе Cortex-M** (`qemu-system-arm`) не выполнялся, проверены только сборка и символы.

### Оценка рассинхрона: `rt_xcorr`
**Метод.** `rt_xcorr_delay_multi` — многоканальная нормированная взаимная корреляция по сдвигам ±L (ковариации каналов суммируются) с параболическим уточнением пика. Без памяти, прямо по входным массивам.

**Защиты:**
- `RT_ERR_LOW_EXCITATION` — суммарная дисперсия окна ниже порога (висение без вращения);
- пик корреляции возвращается вызывающему: ниже 0.9 окно отбраковывается.

**Сигнал.** Три компоненты угловой скорости в связанной системе координат: гироскоп против первой производной ориентации — вектора поворота R[k−2]ᵀR[k+2], делённого на интервал. Первая версия брала модуль |ω|, но при постоянном вращении («бочка») он почти константа: порог возбуждения отбраковал 75 из 80 окон. Компоненты этой информации не теряют.

**Точность** (`xcorr_check.py`): 200 Гц (1 отсчёт = 5 мс), окно 2 с, поиск ±100 мс.

|---|---|
| EuRoC V1_02: собственное смещение IMU относительно истины | −0.11 мс (5–95 %: −0.7…0.2) |
| EuRoC V2_02: то же | −0.02 мс (−0.2…0.1) |
| EuRoC V1_02: введённый сдвиг 5 / 10 / 20 / 50 мс | ошибка: медиана 0.02–0.03 мс, p95 ≤ 0.11 мс; **100 %** окон в пределах 1 отсчёта; отбраковано 2 из 80 |
| EuRoC V2_02: то же | медиана 0.01–0.02 мс, p95 ≤ 0.07 мс; **100 %**; отбраковано 0 из 112 |
| Синтетика 6-DoF, шум позы 1 мм / 0.1° или 2 см / 0.3° | **все окна отбракованы** (пик < 0.9) |

Синтетику отбраковывает сам детектор. Генератор даёт разброс угловой скорости всего 0.06 рад/с, а шум угловой скорости из позы при 0.1° — 0.054 рад/с: отношение сигнал/шум около 1. Медианный пик — 0.57. Без шума позы пик 0.994 — значит, в самом сигнале ошибки нет. Реальный дрон EuRoC вращается до 2.5 рад/с, и там детектор точен. Вывод: оценка рассинхрона требует вращательного возбуждения, а пик корреляции честно сообщает, есть ли оно.

**Цена** (i5-11400H, WSL2, -O2): окно 400 × 3 канала, ±20 сдвигов — 53 мкс по медиане, p99 67–69 мкс. Это около 49 000 умножений; оценка «единицы мкс» в плане S4 была неверной. Детектор нужен раз в окно, например раз в секунду, а не на каждый отсчёт.

## S4, шаг 2: GEP v0.1 Lite — подписанный кадр и защитный слой узла

**Кадр** (`gep_lite.py`, порядок байт big-endian): фиксированный заголовок 22 B, полезная нагрузка фиксированной длины для каждого типа, подпись Ed25519 64 B над заголовком и нагрузкой.

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 2 | magic `GL` |
| 2 | 1 | версия = 1 |
| 3 | 1 | тип: 1 CLAIM, 2 REFUTE, 3 TOMBSTONE, 4 SYNC_PING |
| 4 | 1 | автор (номер узла; ключ — из реестра) |
| 5 | 1 | флаги (0) |
| 6 | 2 | цель |
| 8 | 4 | seq автора, строго растёт |
| 12 | 8 | метка общего времени, мкс (int64) |
| 20 | 2 | длина нагрузки |

| Тип | Нагрузка | Кадр |
|---|---|---|
| CLAIM | x, y, z (float64) | 110 B |
| REFUTE | о ком (u8), причина (u8), резерв, seq заявки (u32) | 94 B |
| TOMBSTONE | кто похоронен, причина, число улик, с какого момента | 98 B |
| SYNC_PING | t_send, t_echo (int64) — для оценки смещения часов | 102 B |

**Порядок проверки при приёме:** длина → magic → версия → тип → длина нагрузки согласована с типом и с размером кадра → автор есть в реестре → подпись Ed25519 → повтор (seq) → метка из будущего (больше `max_skew`). До проверки подписи содержимое кадра не используется.

**Карантин** — локальный, решение принимает сам узел:
- **Битая подпись или испорченный формат** — в карантин идёт **транспортный источник** (адрес), а не автор. Поле «автор» до проверки подписи может подставить кто угодно. Если бы в карантин шёл названный автор, мусором от имени честного узла его можно было бы изолировать. Тест `test_forgery_quarantines_source_not_the_named_author` закрепляет это поведение.
- **Подписанная метка из будущего** — в карантин идёт автор: подпись доказывает авторство.
- **Подтверждённое кинематическое вето** — `veto_k` = 3 опровержения шлюзом за 10 с. В карантин идёт автор, `rt_kin_forget_author` удаляет его отсчёты из колец всех целей, и рассылается TOMBSTONE.
- **Опровергнутая заявка** в кольцо не пишется.
- **Отступ надгробий** (`TombBackoff`, перенесён из v4.0-B): одно надгробие одному соседу уходит через 0, 1, 3, 7, 15 и 31 с, дальше раз в 30 с.

**Карантин источника** (исправлено на шаге 3): только за серию — 3 нарушения за 10 с — и на 30 с, потом реабилитация.

**C99:** `rt_kin_forget_author` удаляет отсчёты автора с сохранением порядка остальных и обнуляет его суммы. После удаления прогноз совпадает с окном, где лжеца не было, до 1e-9. Без malloc, всего 179 C-проверок.

**Тесты** (`tests/test_gep_lite.py`, 7):
- кадры всех типов: упаковка и распаковка, размеры;
- **каждый** из 110 байт кадра с переворотом бита 0x01 и 0x80 (220 вариантов) отвергается;
- коды причин: short, magic, version, type, length, author, signature;
- подделка подписи → карантин источника, автор цел;
- повтор и старый seq → отброшены; задержка доставки — норма; метка из будущего → карантин автора и TOMBSTONE;
- отступ надгробий — отдельный счёт для каждого соседа и каждого надгробия;
- связка с C99-шлюзом: лжец T8 после 2 опровержений на 3-м уходит в карантин, кольцо его забывает, честные заявки ни разу не опровергнуты.

**Цена слоёв на один кадр CLAIM** (`gep_bench.py`; Python 3.14, cryptography 46 / OpenSSL, i5-11400H, WSL2; два запуска):

|---|---|---|

| подпись Ed25519 | 31–33 | 49–58 |

**Вывод для шага 3:**
- Приём кадра на 90 % состоит из проверки Ed25519. Сам шлюз в C — 0.5–0.9 мкс; через ctypes добавляется около 2.5 мкс. UDP на одной машине — около 2 мкс.

## S4, шаг 3: живая шина — 7 процессов ОС по UDP

**Стенд** (`live_bus.py`):
- 7 независимых процессов ОС, у каждого свой PID и свой UDP-сокет на 127.0.0.1;
- реальное время: общий монотонный таймер плюс сдвиг часов узла;
- кадры GEP v0.1 Lite с подписью Ed25519; у каждого процесса свой C99-шлюз (`librt_core.so` через ctypes) и свой локальный карантин.

**Мир** — траектория дрона из EuRoC `state_groundtruth_estimate0`, отрезок 10–40 с полёта.
- Каждый узел — борт-наблюдатель: 25 Гц, заявка «истина + шум σ = 2 см», рассылка 6 соседям; на шине около 175 заявок в секунду.
- Узел 6 — атакующий: с 5-й секунды T8, сдвиг 20–50σ по оси.
- Собственный датчик узла для шлюза — истина + шум, в 5 % случаев грубый сбой.

**Дефекты сети** эмулирует отправитель:
- потеря каждого кадра с вероятностью 0 / 5 / 20 %;
- задержка доставки — равномерно 5–30 мс;
- часы честного узла 2 сдвинуты на +200 или −200 мс.

Пороги в единицах σ, как на EuRoC: горизонт 0.5 с, `thr` 20σ, `pos_tol` 10σ. Вето: 3 опровержения за 10 с. Карантин источника: 3 нарушения за 10 с на 30 с.

**Рассинхрон часов** — два разных механизма:

- **Часы на −200 мс** (узел отстаёт). Его метки выглядят как задержка доставки, и проверка «из будущего» их не ловит. Узел 2 сразу отрезает всех остальных: для него их кадры приходят «из будущего». Исправные изолируют его только по кинематическому вето — через **20.4 с (V1_02) и 28.1–28.4 с (V2_02)**. Ошибка в 200 мс даёт сдвиг больше `pos_tol` = 0.2 м лишь при скорости дрона выше 1 м/с.
- **Вывод:** отстающие часы снаружи по меткам не видны. Нужна оценка смещения часов соседей через `SYNC_PING`: формат кадра есть, обработчика нет. Это открытый пункт.

**Отступ надгробий подтверждён измерением** (потери 5 %, V1_02):
- после изоляции атакующего каждый честный узел отправил в среднем **28.3** кадра надгробий за 25 с — **0.74 кбит/с**;
- по расписанию 0, 1, 3, 7, 15 с с учётом 5 % потерь ожидалось 5 × 6 × 0.95 = 28.5 кадра;
- без отступа (раз в 100 мс) было бы около 1 500 кадров, около 39 кбит/с.

**Нагрузка:**
- **CPU** — 5–8.5 % одного ядра на процесс.
- **Время обработки кадра узлом** (проверка формата, Ed25519, карантин, шлюз, запись) — p50 270–380 мкс, p99 до 670 мкс. Это в 3–4 раза дороже изолированного замера (около 100 мкс): к нему добавляются модель собственного датчика на numpy в Python и 7 процессов на одной машине.
- **Сквозная задержка** от метки заявки до вердикта — p50 17.5–17.8 мс, p99 30 мс. Это почти целиком эмулированная задержка доставки (5–30 мс, в среднем 17.5 мс). Собственная задержка стенда — около 0.3 мс.
- **В сценарии −200 мс** p99 доходит до 229 мс — это устаревшие метки рассинхронизированного узла до его изоляции.

**Трафик 106–158 кбит/с на узел** нельзя сравнивать с бюджетом 45 кбит/с симулятора. Здесь каждая заявка уходит каждому из 6 соседей отдельно (unicast, 110 B), с частотой 25 Гц. При широковещательной или групповой рассылке трафик упадёт примерно в 6 раз. Батчинг заявок под одну подпись не делался.

**Найдено и исправлено на стенде:**
- **Окно повторов.** Строгое правило «номер кадра только растёт» отбрасывало честные кадры, которые обогнали друг друга из-за задержки (REFUTE и CLAIM одного узла). Теперь — окно на 64 номера с битовой картой, как в IPsec.
- **Карантин источника** — теперь только за серию нарушений и на срок, а не навсегда за один битый кадр.

**Ограничения:** все процессы на одной машине; UDP только по loopback, без настоящего радиоканала; наблюдатели и атака смоделированы поверх реальной траектории; Python-уровень.

## S5.1: синхронизация часов (SYNC_PING / PONG) и групповая рассылка

**Задача:** узел с отстающими часами (−200 мс) в S4 отрезал всех соседей, а его самого ловили лишь через 20–28 с; трафик 106–158 кбит/с на узел из-за рассылки каждому соседу отдельно. Цель — выравнивание за ≤ 2 с, трафик < 45 кбит/с, 0 ложных тревог.

**Кадр не меняется** — 102 B, тип 4, нагрузка `>qq`. Используется байт `flags` заголовка: бит 0 — PONG, бит 1 — «часы автора синхронизированы».

| Поле | PING | PONG |
|---|---|---|
| `flags` бит 0 | 0 | 1 |
| `target` | `0xFFFF` (группа) или номер соседа | инициатор |
| `t_us` заголовка | t1 — отправка | t3 — отправка ответа |
| нагрузка | (t1, 0) | (t1 — эхо, t2 — приём PING) |

Инициатор фиксирует t4 и считает задержку δ = (t4 − t1) − (t3 − t2) и смещение соседа θ = ((t2 − t1) + (t3 − t4)) / 2. Все метки под подписью Ed25519; ответ с чужим эхом t1 отбрасывается.

**Алгоритм** (`gep_lite.ClockSync`, без ОС-зависимостей):
- групповой PING раз в 0.5 с; ответ каждому соседу не чаще 3 раз в секунду (защита от флуда, запас на джиттер);
- по соседу хранятся 8 последних замеров, берётся θ с минимальной δ (как в NTP);
- поправка — **медиана** θ по соседям с ≥ 2 замерами, нужно ≥ 3 соседа; свои часы в медиане не участвуют. Из 6 соседей медиану не сдвигают 2 лжеца;
- |медиана| > 20 мс — шаг, замеры и PING в полёте сбрасываются; > 2 мс — подстройка на половину; `locked` — медиана ≤ 20 мс.

**Изменения в защите узла** (`gep_lite.Node`):
- **Льготное окно.** Метка «из будущего» → кадр отбрасывается. Карантин автора — только если он шлёт «будущее» дольше 5 с **и мои часы синхронизированы**: иначе «будущее» может означать, что отстаю я.
- **Шлюз молчит до синхронизации.** Пока свои часы не `locked`, узел не выносит кинематических вердиктов и не кормит кольцо: его датчик читается не в тот момент.
- SYNC-кадры не проходят проверку «из будущего» — метка в них и есть измеряемая величина. Подпись, окно повторов и лимит частоты остаются.

**Транспорт** (`live_bus.py`):
- UDP multicast 239.255.42.99 на loopback: один `sendto` на кадр. У каждого узла свой исходящий порт, так что карантин источника по адресу работает.
- Потери и джиттер эмулирует **получатель**: каждый процесс сам теряет кадр с вероятностью `loss` и задерживает на 5–30 мс. У разных получателей потери разные — модель широковещательного эфира.
- SYNC-кадры, адресованные не мне, отбрасываются до проверки подписи — экономия Ed25519, ничего не принимается.
- Режим `--unicast` — рассылка каждому соседу, для сравнения.

- **Спешащие часы (+200 мс)** — тоже никакого карантина: соседи 0.6 с отбрасывают его кадры (70–74 отброса «из будущего»), потом он выправляется.
- **Лжец в SYNC** со сдвигом +1 с медиану не сдвинул: остаток часов честных ≤ 9.1 мс.
- **Трафик: отправка 29–31 кбит/с, пик 34.8 — цель < 45 взята.** Из них SYNC — 7.7–9.3 кбит/с. Unicast на тех же условиях — 147 / 168 кбит/с: групповая рассылка снижает отправку в 4.9 раза.
- **Надгробия:** 5 кадров на узел, 0.13 кбит/с, против 30 кадров и 0.78 кбит/с при unicast — одно надгробие уходит сразу всей группе.
- CPU 6.8–10.3 % ядра на процесс; обработка кадра p50 280–410 мкс; сквозная задержка p50 18 мс, почти вся — эмулированный джиттер.

**Оговорки:**
- **Точность ограничена асимметрией задержки.** NTP-схема предполагает, что путь туда и обратно одинаков. Ошибка одного замера — до половины асимметрии: при джиттере 5–30 мс в каждую сторону это (30 − 5) / 2 = **12.5 мс**. Поэтому допуск выравнивания — **15 мс**. Фильтр минимальной задержки и медиана дают на практике ≤ 9.1 мс; это внутри порога «из будущего» 50 мс и окна шлюза. При сильно асимметричном реальном канале точность хуже — нужна калибровка канала.
- **«Синхронизирован» ≠ «выровнен».** После шага поправки нужно ещё два круга PING, чтобы признать часы синхронизированными (`locked`). При потерях 20 % последний узел синхронизировался только к 2.2 с; всё это время он не судит.
- **Лжец в SYNC** — тот же узел 6. После 5-й секунды он в карантине за T8 и его PONG отбрасываются. То есть ложь проверена на этапе выравнивания (0–5 с), а не на всём прогоне.
- **Приём 173–187 кбит/с на узел** — честная цифра: в общем эфире слышны кадры всех 7 отправителей. Отправка — это доля эфира, которую занимает сам узел.
- **Unicast здесь не равен S4.** Эмуляция потерь и джиттера перенесена к получателю, а SYNC добавляет 16.7 кбит/с: каждому соседу отдельный PING.
- Все процессы на одной машине, multicast по loopback, без настоящего радиоканала; Python-уровень; наблюдатели и атака смоделированы поверх реальной траектории.
